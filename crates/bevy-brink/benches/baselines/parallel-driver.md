# Scenario harness — PARALLEL-driver baselines (BH-3, issue #927)

Generated by `cargo bench -p bevy-brink --bench scenario_bench -- --mode parallel`. Same axes, story, seed, and setup as `batch-serial-driver.md`, but the batch turn runs through `advance_batch_parallel` (BH-3, #927): the Step phase on `ComputeTaskPool` through an `UnsafeWorldCell`, with Collect, per-flow Step, and the flow-id-ordered Apply shared verbatim with the serial `advance_batch` (the determinism law: parallel ≡ serial-in-flow-id-order, byte-identical). Column mapping matches batch mode: `step p50` is the whole batch turn (command flush included), `apply p50` is the harness's host-side auto-choose pass, `collect p50` reads 0. Expect parity-or-worse at low flow counts (task-spawn overhead) and the win to appear as Step outgrows the fixed per-turn cost. Since #937 there is no per-flow frame-start clone: each flow borrows the frame-start world (§12.2 "borrow, don't copy") and overlays its own writes, so the fixed per-turn cost no longer scales with story-world size — raise `--story-globals N` to see that axis at all. The `ComputeTaskPool` thread count is process-global and printed by the run (`compute_task_pool_threads=`); record it with any capture. See `docs/bevy-bench.md` for the shared honesty caveats.

## Canonical capture (hand-maintained; re-add after regenerating)

**CANONICAL — quiet-window solo run**, captured **2026-07-17** on the same
machine as the canonical serial (PR #916) and batch-serial (PR #929)
baselines: Apple M2 (MacBook Air, Mac14,2), 8 cores (4P+4E), 24 GB RAM,
macOS 26.5.2, rustc 1.97.0, `cargo bench --features bench-counters` (the
`bench` profile, optimized), default 30 frames, per-worktree target dir,
nothing else running. **`ComputeTaskPool` = 4 compute threads** (bevy's
default split on 8 cores: 2 io + 2 async-compute + 4 compute), confirmed
by the run's `compute_task_pool_threads=4` line. Three back-to-back runs
agreed within **~3% on the worst row's `frame p50` (~1–2% typical)** — a
slightly wider band than the serial modes' ~1%, which is honest task-pool
scheduling jitter, not load; the run whose files are checked in sits at
the median of the three. This replaces PR #934's
`parallel-curve-provisional.{csv,md}` (in-wave, one-turn, different flow
axis) as the canonical parallel numbers, per the 2026-07-16 baseline-first
ruling.

(Ratios < 1 mean parallel is faster; as speedups: **1.19× vs serial /
1.01× vs batch at 100 flows, 1.33×/1.34× at 1k, 1.39×/1.50× at 10k**.)

Reading this honestly: on 4 compute threads the parallel Step **wins from
~1k flows up and is parity below it** — the crossover against its own
batch-serial twin sits between 100 (0.99×, inside noise) and 1,000 (0.74×,
a real win). At 1 flow parallel is parity-to-marginally-slower (1.03× vs
batch): one task on a pool cannot beat the same work inline, and the scope
spawn is pure overhead. The **light-turn row is the honest loss**: 1.27×
vs serial — when per-turn VM work is tiny, per-task overhead plus the
per-flow frame-start clone (this capture predates #937; the clone ran *on
the workers*, but was still paid once per flow) dominate the parallelized
Step. The heavy row wins (0.78× vs batch) for the same
reason in reverse. The ceiling is **~1.5× at 10k on 4 workers, not ~4×**:
the Step phase proper speeds up ~1.55× (13.8ms vs batch's 21.4ms at 10k)
— per-flow work is a few µs of VM against a scalar-globals world, so
task-pool dispatch, per-flow clone/allocator pressure, and the serial
tail (flow-id-ordered Apply: 1.04ms at 10k, plus the host auto-choose
pass) bound it, exactly the §12.2 prediction. These are the numbers the
#937 borrow-don't-copy change was judged against — see below.

### #937 "borrow, don't copy" — measured effect (PR for issue #937)

The clone this table's commentary blames is gone: Step now borrows the
frame-start world and overlays each flow's own writes. Two things follow.

1. **On this matrix (`story_globals = 0`) the change is parity.** The
   scenario story declares one to three `VAR`s, so the clone it removes was
   already nearly free — exactly the caveat #937's issue body opens with.
   The canonical captures above therefore still stand as the numbers for
   this matrix; they have deliberately not been regenerated, both because
   a re-capture needs the ruled quiet-window solo run and because a parity
   change is not a reason to churn a hand-maintained baseline. See
   `batch-serial-driver.md`'s "#937 measured effect" section for the
   batch-serial A/B this predicts (0.289 → 0.288 ms at 100 flows,
   2.440 → 2.402 ms at 1k, 25.736 → 25.018 ms at 10k, 0.163 → 0.158 ms at
   100-light) — the batch-serial driver is the primary home for that data
   since it is the driver `--story-globals N` axis was added against; this
   file only reports the parallel driver's own numbers below.
2. **On a real-sized story world the change is large.** `--story-globals
   1000` (#937's brink-`World` axis, added with that PR) at 20 frames,
   parallel, median of 3 alternating pairs:

   | flows | before p50 (ms) | after p50 (ms) | speedup |
   |---:|---:|---:|---:|
   | 1,000 | 2.899 | 2.106 | 1.38× |
   | 100 (light) | 0.327 | 0.223 | 1.47× |

   Its 10k row was **not** resolvable: that capture ran at load average
   ~16 with other builds on the machine, and the 10k row's run-to-run
   spread (21.4–43.1 ms after, 29.5–31.6 ms before) swamps the effect.
   Treat every number in this subsection as a **relative, same-session
   A/B**, not a canonical capture — it was taken on a loaded machine and
   only the pairing is trustworthy.

One worker costs ~4–10% over the serial batch driver (the scope machinery
itself, an honest floor); scaling 1→4 workers is ~1.56× at 10k (see the
ceiling note above); 8 workers on 8 cores (4P+4E, sharing with the main
thread + io/async pools) still edges out 4 slightly at 10k — the E-cores
contribute, but far below linearly.
