# E168

## Summary

Two `@[element(claims = "…")]` handlers declare byte-identical patterns, and the later-declared one never actually won a claim in this file — it is dead code.

## Explanation

Issue #1838 rewrote every prose line a claiming handler's pattern matches into exactly one call. When a file declares more than one claiming handler, and more than one of them could match the same line, something has to decide which handler wins — and today (issue #1848) that something is **declaration order**: `try_claim` (`crates/internal/brink-ir/src/hir/lower_native/element.rs`) tries each handler in the order it was declared and dispatches to the first pattern that matches.

**This is an interim rule, not a permanent one.** The 2026-07-31 §9.1 ruling's item (5) (`docs/decision-log.md`) says a `fn conventions()` well-known entry will eventually **register** handlers in order (issue #1840), and *that* registration order — not a claiming `fn`'s textual position in the file — becomes the authoritative resolution order once it lands. Until then, declaration order is the only order there is.

`E168` catches the narrowest, fully provable instance of two patterns competing for the same line: **identical patterns**. Identical patterns match identical inputs, so wherever both handlers are eligible to claim a line, the earlier one wins first.

That is not quite the same as "the later declaration can never claim anything", though. `try_claim` excludes a handler from claiming lines that live inside its **own** declaration (a handler's own body is not claimable by itself — the staging rule). That exclusion does not extend to a later, byte-identical twin: the twin is exactly the handler that *can* claim a line inside the earlier one's own body, precisely because the earlier one is barred from claiming there. So `E168` runs after the whole file has been lowered and only fires when the later twin produced **zero** actual claims — a twin that won even one claim (necessarily somewhere inside an earlier twin's own body) is live and is not diagnosed.

**What this does not catch.** Two *different* patterns whose matched-line sets merely overlap — one a strict subset of the other, an alternation sharing a branch, two competing prefixes — are the more common and more valuable case to flag ("pattern power proportional to auditability", `docs/prose-dialect-spec.md` §3.5b). That case is now covered by `E170` (issue #1859), which proves subsumption from a set of witness strings generated from the later pattern's structure rather than requiring byte-identical text.

## Example

```brink
@[element(claims = "^(?<who>[A-Z]+) enters$")]
fn arrival(who) {
  return who;
}

@[element(claims = "^(?<who>[A-Z]+) enters$")]
fn arrival_again(who) {
  return who;
}
```

`arrival_again`'s pattern is byte-identical to `arrival`'s, and neither declaration's own body contains a line either pattern matches, so `arrival_again` never wins a single claim in this file — dead code.

## Fix

Either remove the duplicate declaration, or — if the two handlers are meant to do different things for the same shape of line — merge them into one handler, since two claims on the same pattern can never both fire on the same line.

```brink
@[element(claims = "^(?<who>[A-Z]+) enters$")]
fn arrival(who) {
  return who;
}
```

**Caution before deleting**: check `arrival`'s own body first. A handler can never claim a line inside its own declaration (the staging rule), so if `arrival`'s body itself contains a line `arrival_again`'s pattern matches, `arrival_again` is the one actually claiming it — and this diagnostic would not have fired for that case (it only fires when the later handler won zero claims). If it did fire, the later handler is genuinely unreachable and safe to remove.
