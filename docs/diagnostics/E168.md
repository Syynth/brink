# E168

## Summary

Two `@[element(claims = "…")]` handlers declare byte-identical patterns. The later-declared one can never claim anything the earlier one didn't already claim first.

## Explanation

Issue #1838 rewrote every prose line a claiming handler's pattern matches into exactly one call. When a file declares more than one claiming handler, and more than one of them could match the same line, something has to decide which handler wins — and today (issue #1848) that something is **declaration order**: `try_claim` (`crates/internal/brink-ir/src/hir/lower_native/element.rs`) tries each handler in the order it was declared and dispatches to the first pattern that matches.

**This is an interim rule, not a permanent one.** The 2026-07-31 §9.1 ruling's item (5) (`docs/decision-log.md`) says a `fn conventions()` well-known entry will eventually **register** handlers in order (issue #1840), and *that* registration order — not a claiming `fn`'s textual position in the file — becomes the authoritative resolution order once it lands. Until then, declaration order is the only order there is.

`E168` catches the narrowest, fully provable instance of two patterns competing for the same line: **identical patterns**. Identical patterns match identical inputs, so the overlap is certain, not merely suspected — every line the later handler could ever claim, the earlier one already claims first, silently. That makes the later declaration dead code.

**What this does not catch.** Two *different* patterns whose matched-line sets merely overlap — one a strict subset of the other, an alternation sharing a branch, two competing prefixes — are the more common and more valuable case to flag ("pattern power proportional to auditability", `docs/prose-dialect-spec.md` §3.5b), and they are **not** detected by this code. Proving that soundly needs either a witness string demonstrably accepted by both patterns or a full regex-intersection analysis, and this issue's slice does not build either. It is a tracked gap, not a silent one — see the issue thread for the follow-up.

## Example

```brink
@[element(claims = "^(?<who>[A-Z]+) enters$")]
fn arrival(who) {
  return who;
}

@[element(claims = "^(?<who>[A-Z]+) enters$")]
fn arrival_again(who) {
  return who;
}
```

`arrival_again`'s pattern is byte-identical to `arrival`'s. `arrival` always wins under the interim first-match-wins order, so `arrival_again` can never claim anything.

## Fix

Either remove the duplicate declaration, or — if the two handlers are meant to do different things for the same shape of line — merge them into one handler, since two claims on the same pattern can never both fire.

```brink
@[element(claims = "^(?<who>[A-Z]+) enters$")]
fn arrival(who) {
  return who;
}
```
