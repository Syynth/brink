# E178

## Summary

A `@[convention(claims = "…")]` annotation has no `order` clause.

## Explanation

Issue #2164 (`docs/decision-log.md` 2026-08-03, "`order` is REQUIRED on `@[convention]`, and duplicates within a module are a compile error") split the old `@[element(claims = "…")]` spelling into its own `@[convention(…)]` annotation, and made `order` a **required** property of it, not an optional one:

> `order` is a REQUIRED property of `@[convention]`, not an optional one... there is no "default when `order` is absent", because it can never be absent.

A pattern-claiming handler competes for prose lines it did not announce — unlike a `!name`-dispatched `@[element(…)]` handler, which self-announces and therefore needs no precedence at all. When more than one claiming handler in a module could match the same line, something has to decide which one is tried first. Before this ruling that "something" was implicit: a claiming `fn`'s own textual position in the file. That interim rule (issue #1848) is retired — precedence is now **total, explicit, and authored** on the declaration itself, via `order = N`, and the compiler never falls back to declaration position, file order, or any other inferred tie-break to decide.

Because there is no default, a `@[convention]` written without `order` is not silently assigned "declared-order" precedence the way it would have been before this ruling — it is a compile error instead, so an author is never surprised by a claiming handler's place in the resolution order they never actually chose.

`@[element(args = "…")]` (the `!name`-dispatched, self-announcing form) is unaffected: it takes no `order` at all, since a handler that names itself never competes for a line, and declaring one there is simply an unrecognized clause (`E159`), not this code.

## When this fires

Only for a `@[convention(…)]` annotation (issue #2164's claiming-only name) whose argument list has no `order = N` clause — whether `order` is omitted entirely, or every other clause is well-formed and only `order` is missing.

A `@[convention(…)]` that is otherwise malformed (a missing/non-string `claims` value, a bad regex, an unrecognized clause key) is diagnosed as `E159` instead — `E178` fires only once the annotation's other clauses are known-good and `order` specifically is the missing piece.

## Example

```brink,fires(E178)
@[convention(claims = "^INT\\. (?<place>.+)$")]
fn interior(place: content) {
  return "-- inside {place} --";
}
```

`interior` claims scene headings but declares no `order` — `E178`.

## Fix

Add an explicit `order = N` clause naming this handler's precedence among the module's other claiming handlers:

```brink,contrast
@[convention(claims = "^INT\\. (?<place>.+)$", order = 10)]
fn interior(place: content) {
  return "-- inside {place} --";
}
```

Lower values are tried first. Adding a handler to a dense module may mean renumbering its neighbours — an accepted, known cost (`docs/decision-log.md` 2026-08-03): it is paid once, in a file that is small, authored rarely, and reads top-to-bottom as the precedence order it encodes. Sparse numbering (`10`, `20`, `30`, …) is a documentation convention worth adopting for exactly this reason, though the language itself attaches no meaning to the gaps.
