# E170

## Summary

Two `@[element(claims = "…")]` handlers declare textually different patterns that can both match the same line of prose, and the later-declared one never actually won a claim in this file — it is unreachable.

## Explanation

This extends `E168` (byte-identical patterns) to cover the more common and more valuable case: two *different* patterns whose matched-line sets overlap.

When a file declares more than one claiming handler, and more than one of them could match the same line, something has to decide which handler wins — and today (issue #1848) that something is **declaration order**: `try_claim` (`crates/internal/brink-ir/src/hir/lower_native/element.rs`) tries each handler in the order it was declared and dispatches to the first pattern that matches.

**This is an interim rule, not a permanent one.** The 2026-07-31 §9.1 ruling's item (5) (`docs/decision-log.md`) says a `fn conventions()` well-known entry will eventually **register** handlers in order (issue #1840), and *that* registration order — not a claiming `fn`'s textual position in the file — becomes the authoritative resolution order once it lands. Until then, declaration order is the only order there is.

`E170` catches overlapping (but non-identical) patterns where the later handler provably can never match — because the earlier handler's pattern covers all the cases the later one could match, and the earlier one always wins first.

The detection uses a sound-but-incomplete heuristic: finding a concrete witness string that both patterns match. If one is found, the patterns provably overlap. The heuristic examines:

- **Shared literal prefixes** — if both patterns start with the same fixed text (e.g., both match lines starting with "INT. "), they can only both match strings with that prefix
- **Pattern structure expansion** — trying to generate minimal example strings from each pattern's literals, character classes, and repetitions, and testing if both patterns accept the example
- **Fallback test strings** — common test inputs like empty string, single characters, etc.

A witness found proves overlap; none found does not prove they never overlap (the heuristic is incomplete). Only reports what it can prove.

The later handler is only flagged if it produced **zero** actual claims — if it actually won even one claim (necessarily for a line the earlier pattern couldn't match, or where the earlier pattern was barred by the staging rule), it is live and is not diagnosed.

**What this does not catch.** Overlaps so subtle that no simple witness exists are not detected. For example, two patterns with complex alternations or look-ahead assertions might overlap but not match any of the generated witnesses. This is acceptable — a false negative (missing a real overlap) is safer than a false positive (incorrectly flagging patterns that never actually overlap).

Each later handler is reported **at most once**, against the first (source-order) earlier handler it provably overlaps with — a handler that overlaps two or more earlier ones is not re-reported once per overlap.

## Example

```brink
@[element(claims = "^(?<who>[A-Z]+) enters$")]
fn arrival_general(who) {
  return who;
}

@[element(claims = "^(?<who>VENDOR) enters$")]
fn arrival_vendor(who) {
  return who;
}
```

Both patterns match "VENDOR enters":
- `^(?<who>[A-Z]+) enters$` matches any all-caps word followed by " enters"
- `^(?<who>VENDOR) enters$` matches only "VENDOR enters"

The second pattern is a subset of the first, so they overlap. Under the interim first-match-wins order, `arrival_general` always wins first, so `arrival_vendor` never gets to claim anything. If neither handler claims a line inside its own declaration (the staging rule applies equally to both), then `arrival_vendor` is dead code.

## Fix

Either remove the later, unreachable handler, or — if the two handlers are meant to do different things — split the prose so that lines the later pattern matches are declared inside the earlier handler's own body, where the staging rule gives the later handler a chance to claim.

```brink
@[element(claims = "^(?<who>[A-Z]+) enters$")]
fn arrival_general(who) {
  return who;
}

@[element(claims = "^(?<who>VENDOR) enters$")]
fn arrival_vendor(who) {
  return who;
}

flow scene() {
  ALICE enters     // claimed by arrival_general
  VENDOR enters    // also claimed by arrival_general
}
```

In the above example, `arrival_vendor` never wins a claim, so this diagnostic fires.

To make `arrival_vendor` live, you'd need to ensure it can claim a line that `arrival_general` cannot (impossible if the second pattern is truly a subset) or where `arrival_general` is barred by the staging rule:

```brink
@[element(claims = "^(?<who>[A-Z]+) enters$")]
fn arrival_general(who) {
  // Put a VENDOR line inside this handler's own body.
  // arrival_general is barred from claiming it (staging rule),
  // so arrival_vendor gets a chance.
  VENDOR enters    // claimed by arrival_vendor
  return who;
}

@[element(claims = "^(?<who>VENDOR) enters$")]
fn arrival_vendor(who) {
  return "vendor: " + who;
}
```
