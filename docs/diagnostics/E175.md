# E175

## Summary

`register` is called somewhere other than inside the project's configured conventions module's `fn conventions()`.

## Explanation

The 2026-08-02 ruling ("`register` is a comptime-only intrinsic; calling it elsewhere is a diagnostic", `docs/decision-log.md`, issue #1840 Q5) settles `register`'s lowering and legality:

> `register` is a T1b intrinsic, legal ONLY inside the conventions module's `fn conventions()`, where the comptime evaluator intercepts it during `begin_function_eval`. No opcode, no runtime registry cell, no bytecode — `fn conventions()` is comptime-consumed and never emitted, so the registry has no runtime life. Calling `register` anywhere else is a compile error.

`register`'s whole purpose is to record, in declaration order, which annotated handlers the project's conventions module wants to claim prose with (`docs/decision-log.md`'s 2026-07-31 "Conventions are annotated handlers" ruling, item 5). That only means something inside the one well-known function the compiler comptime-evaluates for that ordered list. Everywhere else, a call to `register` cannot be serviced — there is no comptime evaluator running, no registry to write, and (per the ruling) no ordinary runtime fallback either: a call that silently did nothing would be exactly the silent data drop `CLAUDE.md` forbids.

## When this fires

Any call to a bare (unqualified) `register(...)` that is not textually inside the top-level `fn conventions()` declared in the project's configured conventions module (`brink.toml`'s `[project] elements`, when it names a project-relative `.brink` path that actually resolves to a file in the project). This includes:

- `register(...)` called from any other function, anywhere in the project — including elsewhere in the conventions module itself.
- `register(...)` called from a file that is *not* the project's configured conventions module, even if that file also happens to declare its own `fn conventions()`.
- `register(...)` called anywhere at all when `[project] elements` is unset, names a bare preset (e.g. `elements = "screenplay"`), or names a path that resolves to no real file — there is no confined module for any call to be "inside", so every use is illegal.

## Example

```brink
// scenes/heading.brink
fn setup() {
  register(interior)
}
```

`register` is called from `setup`, not from `fn conventions()` — `E175`, regardless of whether this file is the configured conventions module.

## Fix

Move the call into the conventions module's `fn conventions()`:

```brink
// conventions.brink — the file brink.toml's `elements` key names
use std::conventions::screenplay

fn conventions() {
  register(screenplay::scene)
  register(interior)
}
```

Statement order is resolution order — list handlers in the order you want them tried.

## `register`'s effect row

`docs/decision-log.md`'s 2026-08-01 Q4 ruling settles what `register` *means* in the effect system — a write to a named registry cell, same shape as every RNG draw (`docs/effects-spec.md` §10) — correcting an earlier framing that failed its own `E103` fence. This is now wired (issue #1840's registration slice, 2026-08-02): `register` writes `DefinitionId::CONVENTIONS_REGISTRY_CELL`, spelled `conventions_registry` in a `writes(…)` clause. `@[effects(pure)] fn conventions() { register(x) }` — the ruled example's original spelling — correctly fails `E103`; `@[effects(writes(conventions_registry))]` is the spelling that passes. This diagnostic (`E175`, legality/confinement only) is a separate pass, unaffected either way. See `docs/effects-spec.md` §10 and §14.5 item 3 for the full history.
