# E035

## Summary

Name shadows a built-in function.

## Explanation

`brink-analyzer::manifest`'s symbol-declaration pass warns whenever an
author declares a `VAR`, `CONST`, `EXTERNAL`, or knot (including a
`=== function NAME(...) ===` tunnel-as-function) whose name collides with
one of two reserved-name sets: the classic uppercase ink intrinsics
(`is_builtin_function` — `RANDOM`, `FLOOR`, `TURNS_SINCE`, …) or the T1b
stdlib slice-1 lowercase free functions (`is_t1b_stdlib_name` — `len`,
`push`, `insert`, `remove`, …, brink-dialect only). The bare `none` Option
literal rides the same warning for the same reason, though it is not a
function name at all. This is the ruled posture, stated in
`docs/t1b-surface-spec.md` §5 and `docs/stdlib-spec.md` item 3: prelude and
builtin names are **shadowable, not reserved** — an author declaration of
the same name is legal, and E035 exists only to flag that it is happening,
not to block it. (The one exception is the protocol registry's `display` /
`compare` / `next` — those three names are a **hard compile error** to
redeclare, not an E035 warning; see `docs/stdlib-spec.md` item 6, F6.)

The warning fires once, at the shadowing symbol's own **declaration site**,
in the "merge manifests" step of analysis (`docs/compiler-spec.md` Pass 3) —
independent of whether the symbol is ever referenced or called anywhere in
the program. `SymbolKind::List` and `SymbolKind::ListItem` are **not** in
the warned-kind set. That is not a gap: see "What does NOT fire" below for
why a list item colliding with a stdlib verb name has nothing to warn
about.

Until PR #2859 (issue #2856), this rule was **documented but not actually
implemented**: `resolve_variable`/`resolve_function` (and, independently,
`lir::lower::expr::lower_call`) checked the reserved-name sets *before*
consulting real declared symbols, so a `VAR RANDOM` was silently ignored in
favor of the real `RANDOM()` at every read, and a knot `=== function
FLOOR(x) ===` was silently ignored in favor of the real `FLOOR()` at its own
call site — a clean compile with the E035 warning present, and the wrong
program running underneath it. PR #2859 reordered both layers so a real
resolved declaration wins first, with builtin recognition demoted to a
fallback consulted only once resolution has already failed — the "rules
attach to resolved definitions, never names" ruling (`docs/decision-log.md`,
2026-07-12). This page documents the rule as it now actually behaves.

## When this fires

E035 fires once per declaration, for any `VAR`, `CONST`, `EXTERNAL`, or
knot (function or otherwise — ink allows any knot to be called as a
function via tunnels) whose name is a reserved builtin or stdlib name, or
is literally `none`. It does not matter whether the dialect is `strict-ink`
or `brink`, or whether the declaration is ever referenced — declaring `VAR
RANDOM = 42` and never using it still warns.

## What happens at a call site (the subtle part)

Compiled and run end-to-end for this page (`crates/brink-compiler/tests/
issue_2856_builtin_shadow.rs`), the five shapes below do **not** all behave
the same way, and that is by design, not an inconsistency:

| Shape | Declaration | Read/call | Result |
|---|---|---|---|
| `VAR` read | `VAR RANDOM = 42` | `{RANDOM}` | prints `42` — **the VAR wins** |
| Knot called | `=== function FLOOR(x) === \n ~ return x - 1000` | `{FLOOR(5)}` | prints `-995` — **the knot wins** |
| `VAR` called | `VAR MAX = 10` | `{MAX(1, 2)}` | prints `2` — **the real `MAX()` builtin wins**, not the VAR |
| `CONST` called | `CONST MAX = 10` | `{MAX(1, 2)}` | prints `2` — **the real `MAX()` builtin wins**, not the CONST |
| `LIST` item bare-read | `LIST Ops = alpha, push, gamma` | `{push}` | prints `push` — **the list item wins**, no E035 warning at all |

A **bare read** of a shadowing `VAR`/`CONST` always resolves to the
declared symbol (`resolve_variable`'s own resolution step runs before the
builtin-name fallback). A **call site** (`{NAME(args…)}`) is where the
kinds diverge:

- **`EXTERNAL` and knots are genuinely callable**, so `resolve_function`
  tries them first, unconditionally — a shadowing external or knot always
  wins its own call site, matching ink's own tunnel-as-function semantics.
- **`VAR` and the `list(n)` conversion form are looked up next, but gated**:
  `resolve_function` only tries `SymbolKind::Variable`/`SymbolKind::List`
  when the callee name is *not* a reserved builtin/stdlib name at a real
  call site (`arg_count.is_some()`). A `VAR` is not itself callable the way
  a knot is or a variable-holding-a-divert-target is dynamically dispatched
  — routing a reserved-name call through to the real builtin instead is a
  clean compile with well-defined behavior. This is PR #2859's own review
  fix: before it, `VAR MAX = 10` + `{MAX(1, 2)}` compiled clean with no
  diagnostic and then **died at runtime** with
  `RuntimeError::NotCallable("int")`, because the unconditional `Variable`
  lookup claimed the call site and lowered it to `CallVariable` against a
  plain int. The guard (`reserved_call_site` in
  `brink-analyzer::resolve::resolve_function`) keeps that call routed to the
  real builtin instead.
- **`CONST` is never looked up as a call target at all** —
  `resolve_function` has no `SymbolKind::Constant` lookup branch anywhere
  in its call-resolution chain (only bare reads reach `SymbolKind::Constant`,
  via `resolve_variable`). A `CONST`-named-after-a-builtin call therefore
  reaches the same fallback a `VAR` reaches after its guard, but by a
  different mechanism: not "resolved, then declined," but "never a
  candidate to begin with." The observable *outcome* is identical to the
  `VAR` case — the real builtin runs — which is why the table above shows
  the same `2` for both rows.
- **A non-reserved `VAR`/`CONST` called against an incompatible value is a
  separate, orthogonal story**: `VAR foo = 10` + `{foo(1, 2)}` still
  compiles clean (nothing here reserves `foo`) and still faults at runtime
  with `NotCallable("int")` — that is *not* an E035 shape at all, just
  ordinary ink semantics for calling a variable that does not hold a divert
  target. E035's guard only changes what happens when the name is *also* a
  reserved builtin/stdlib name; it does not make every `VAR` call
  statically checked.

## What does NOT fire

- A `LIST` item's name colliding with a stdlib verb (e.g. a list `Ops`
  containing an item literally named `push`) never gets an E035 warning,
  because `SymbolKind::List`/`SymbolKind::ListItem` are not in the warned
  set. This is not an oversight: a bare reference to `push` (`{push}`,
  `arg_count.is_none()`) resolves to the list item, while a *call* to
  `push(arr, 3)` (`arg_count.is_some()`) still resolves to the real stdlib
  verb regardless of the list item's existence — the two forms occupy
  disjoint syntactic positions (bare-name value read vs. call-with-args)
  that never actually collide. Nothing is silently overridden either way,
  so there is nothing for a shadow warning to report.
- Redeclaring one of the protocol registry's reserved names (`display`,
  `compare`, `next`) is a **hard compile error**, not E035 — see
  `docs/stdlib-spec.md` item 6, F6. These three names are reserved, not
  merely shadowable, because interpolation and sorting depend on them
  meaning one fixed thing.
- An *unshadowed* builtin call (no author declaration of that name exists
  anywhere) never triggers E035 — the warning is about a real declaration
  colliding with a reserved name, not about calling the builtin itself.

## Example

```ink
VAR RANDOM = 42

The value is {RANDOM}.
-> DONE
```

warns `E035: name shadows a built-in function: \`RANDOM\`` at the `VAR`
declaration, and still prints `The value is 42.` — the author's `VAR` wins
the bare read.

```ink
Result: {FLOOR(5)}
-> DONE

=== function FLOOR(x) ===
~ return x - 1000
```

warns the same way at the knot's declaration, and prints `Result: -995` —
the author's knot wins its own call site, exactly like calling any other
knot as a function via ink's tunnel convention.

```ink
VAR MAX = 10

value: {MAX(1, 2)}
-> DONE
```

warns at the `VAR` declaration too, but prints `value: 2` — the call site
falls through to the real `MAX()` builtin, because a plain `VAR` cannot
claim a reserved name at a real call site (see the table above). Declaring
`CONST MAX = 10` instead produces the identical `value: 2` output, for the
different reason given above.

All four shapes are pinned end-to-end (compile + run) in
`crates/brink-compiler/tests/issue_2856_builtin_shadow.rs` —
`var_shadows_builtin_at_read_site`, `knot_shadows_builtin_at_call_site`,
`var_named_builtin_is_not_callable_at_call_site`, and
`const_named_builtin_is_not_callable_at_call_site`. The `LIST`-item shape is
pinned in the same file's
`list_item_shadows_stdlib_verb_name_at_bare_reference_without_e035_warning`
and `list_item_named_push_does_not_break_the_real_push_call`.

## Fix

This is a warning, not an error — the program compiles and the shadowing
declaration is legal. Three responses are reasonable depending on intent:

- **If the collision is accidental**, rename the declared symbol to
  something that does not match a reserved builtin/stdlib name.
- **If the shadowing is intentional and a knot/external**, no action is
  needed — a shadowing knot or external genuinely wins its own call site,
  exactly as intended.
- **If the shadowing is a `VAR`/`CONST` intended to be *called*
  dynamically**, be aware that a call site with a reserved name always
  reaches the real builtin instead, never the `VAR`/`CONST` — this differs
  from a knot or an external. If dynamic dispatch through a variable is the
  actual goal, hold the divert target in a variable with a name that is
  *not* a reserved builtin/stdlib name, so the call site has no ambiguity
  to resolve.
- **To silence the warning without renaming**, suppress it explicitly with
  `@[allow(E035)]` on the declaration (native surface) or the equivalent
  `brink-disable`/`brink-expect` directive.
