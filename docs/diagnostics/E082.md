# E082

## Summary

A T1b block-scoped `temp` (`~ { … }`) — or a `for`-loop variable, which desugars the same way — was referenced (by value or by `ref` argument) after its own `~ { … }`/`while`/`for`/`if` block already closed. Root-caused for #680: LIR lowering's fallback for "temp not currently visible" (then used for inklecate-compat forward-reference emulation of *classic* temps) previously also caught this case, silently emitting a phantom hashed `GetGlobal`/`RefGlobal` id that was never registered as a real global — a runtime-only `UnresolvedGlobal` fault with no compile diagnostic. Issue #3362 has since retired that emulation for classic temps too; see "Plain classic temps behave differently" below and [E193](E193.md).

## Explanation

A block-scoped `temp` — one declared inside a `~ { … }` multi-line logic block, or inside the block a `while`/`for`/`if` opens (`docs/t1b-surface-spec.md` §2) — is visible only for the rest of *that* block. Once the block's closing `}` (or, for `for`/`while`/`if`, the end of the construct it desugars into) is reached, the name goes out of scope, exactly like a local variable leaving a `{ … }` scope in a C-family language. This is a **brink-extension (T1b) construct**: it exists under `--dialect brink` (or `[project] dialect = "brink"` in `brink.toml`); under the default `strict-ink` dialect, `~ { … }` itself is rejected first, by [E051](E051.md), so E082 can never fire there.

The confusing part is that the declaration is still sitting right there in the source, a few lines up — nothing about the shape of the code signals that it stopped applying. `lower_path` (the by-value/`ref`-argument read path) and `lower_call` (the call-position path, added by #2848 for issue #2837) both resolve a bare name to a `Temp` symbol first via `LowerCtx::temp_slot`, which only consults currently-*open* block scopes. When a name was *at some point* declared with `declare_block_local` (i.e. it really is a block-scoped temp, not a classic one) but has nothing open for it right now, that is unambiguous: the block it belonged to already closed, and this diagnostic fires — naming the block-close, not silently falling through.

This mechanism is shared LIR lowering, reached from both source surfaces: ink's own `~ { … }` block syntax, and the native `.brink` surface's own code-ground logic blocks, which lower through the identical scope-tracking pass (see the native lowering's own cross-reference to this exact E082 arm in `hir::lower_native::body::mark_split_logic_block_scopes`'s doc comment, guarding a `> text` prose-line split against attributing a later read to the wrong block).

**Plain classic temps behave differently.** A *classic* `temp` — one declared directly in a knot/stitch body, not inside a nested block — used before its own declaring statement is a forward reference on the flow graph, not a lexical-scope defect: it lives in the same call frame, so since issue #3362 it resolves to that frame's own slot (`temp_slot_raw`) and is reported as [E193](E193.md), a `[lints]`-overridable warning, while the runtime reads the still-unset slot as ink's missing-variable default. (Until #3362 it emitted a hashed `GetGlobal`/`RefGlobal` id — matching how the converter's own hashing works — with no compile diagnostic at all, which failed at link with `unresolved global`.) A block-scoped temp read after its block closes gets the opposite treatment on purpose — it is unambiguously a real defect, and one that was never expressible in inklecate at all, so it is refused at compile time instead of deferred to a runtime fault (the #680 root cause this diagnostic replaced).

## Example

Both shapes below require `--dialect brink` to reach at all (the `~ { … }` block syntax itself is a brink extension — see `E051` — so these do not compile under the default `strict-ink` dialect).

**By-value / `ref`-argument reference** (`lower_path`, the original path):

```ink,fires(E082)
VAR gold = 100
~ {
    temp name = "hero"
}
{name}
-> END
```

compiles with:

```
[E082] block-scoped temp referenced after its block has closed: `name` was declared in a `~ { … }` block that has already closed — block-scoped temps (docs/t1b-surface-spec.md §2) are only visible for the rest of their own block
```

Passing the same out-of-scope name by `ref` (e.g. `~ heal(name)` calling `=== function heal(ref hp) ===`) reaches the identical check inside `lower_call_args`'s `ref`-argument lowering and reports the same message.

**Call shape** (`lower_call`, new in #2848 for issue #2837 — calling the block-scoped temp itself, rather than reading it):

```ink,fires(E082)
VAR gold = 100
~ {
    temp f = 1
}
~ f()
-> END
```

compiles with:

```
[E082] block-scoped temp referenced after its block has closed: `f` was declared in a `~ { … }` block that has already closed — block-scoped temps (docs/t1b-surface-spec.md §2) are only visible for the rest of their own block
```

All three sites — `lower_path`, the `ref`-argument arm, and `lower_call` — emit byte-identical message text, since all three exist for the same author mistake.

## Fix

Either hoist the `temp` declaration out of the block entirely, as a classic (non-block) temp whose scope covers every place it is used:

```ink,contrast
VAR gold = 100
~ temp name = "hero"
{name}
-> END
```

or move every use inside the block that declares it, so nothing outlives the scope:

```ink,contrast
VAR gold = 100
~ {
    temp name = "hero"
    heal(name)
}
Done.
-> END

=== function heal(ref hp) ===
~ return hp
```

## Forward references — see E183, not E082

A block-scoped temp *called* **before** its own declaration (rather than after its block closed) does not reach this diagnostic — `ctx.temp_slot` has nothing open for the name at either point, so `lower_call`'s resolved-target match falls through to its generic non-callable-symbol refusal instead, reported as [E183](E183.md) ("used here before its declaration — it is not in scope at this call site"). E183's own doc names this same distinction from its side. The two mistakes have a similar feel — a name that looks like it should resolve, and doesn't — but they are different defects: E183 is a temporal ordering problem (the declaration hasn't run yet), E082 is a lexical scoping problem (the declaration's block already ended). An author who hits one may well land on the other's page first; if so, this section (and E183's own "What does NOT fire") is the pointer to the right one.
