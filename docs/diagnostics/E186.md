# E186

## Summary

A `@[convention(…)]` declaration combines `block` and `attach = StructName` on the same handler — mutually exclusive clauses.

## Explanation

`try_claim` (`brink_ir::hir::lower_native::element`) dispatches a claimed line to exactly one of two shapes, chosen by an `if is_block { .. } else if is_attach { .. }`: **wrap mode** (`block`, issue #1839) captures the following run into the handler's own trailing `content`-typed parameter, and **attach mode** (`attach = StructName`, issue #2178) captures the following run as block-level metadata, merging the handler's returned struct fields into `OutputLine.element.data` for every line in that run (issue #2108, `docs/decision-log.md` 2026-08-03 "The element output model").

Before this code existed, nothing checked whether a single handler declared both. `parse_convention_clauses`/`convention_annotation` (`annotation.rs`) parsed and stored `attach` regardless of `block`, and `try_claim`'s `if`/`else if` always took the `block` arm when both were set — `attach` was accepted syntax that silently did nothing: no event, no data merge, no error, no warning, no hint. Issue #2264 names this exactly the shape house rule 9 ("flag silent data drops") calls always-a-bug-until-proven-otherwise.

This code is a deliberate refusal to define combined semantics, not an oversight of one: "wrap AND attach" — does the wrapped call's own return value *also* attach to the run it wraps? does it attach to itself? — is an open design question with no ruling and no test pinning any answer. Rather than invent one, `parse_convention` rejects the co-occurrence outright, the same "never a partial `ConventionAnnotation`" posture [E159](E159.md)/[E166](E166.md)/[E167](E167.md)/[E178](E178.md)/[E180](E180.md) already take — a handler declaring both is never registered as a claiming handler at all.

Reachable through both element shapes `try_claim` dispatches: an ordinary block-form claim (`@NAME` on its own line) and the compact-cue desugar (`@NAME: text`, issue #2079) — both route through the same function, so a compact-cue-claiming handler declaring both clauses hits this same check.

## When this fires

- A single `@[convention(…)]` declaration carries both the bare `block` clause and an `attach = StructName` clause, in either order (`block, attach = Cue` and `attach = Cue, block` diagnose identically).

## What does NOT fire

- `block` alone, with no `attach` clause.
- `attach = StructName` alone, with no `block` clause.
- `block` and `attach` declared on two *different* handlers — each handler is checked independently; only one handler declaring both clauses triggers this.

## Example

```brink
struct Cue {
  speaker: string,
}

@[convention(claims = "^(?<name>[A-Z]+)$", order = 10, block, attach = Cue)]
fn cue(name: string, body: content): Cue {
  return Cue { speaker: name };
}
```

`cue` declares both `block` and `attach = Cue` — `E186`, reported at the `@[convention(...)]` annotation line. The declaration is rejected outright: `cue` is never registered as a claiming handler, so a line like `VENDOR` in a flow body is left unclaimed rather than silently rewritten to a call whose `attach` clause does nothing.

## Fix

Pick exactly one mode for the handler:

- **Wrap mode** — the handler re-emits the captured run as part of its own content. Drop `attach`:

  ```brink
  @[convention(claims = "^(?<name>[A-Z]+)$", order = 10, block)]
  fn cue(name: string, body: content) {
    return "{name}: {body}";
  }
  ```

- **Attach mode** — the handler's own claimed line consumes itself and tags the following run with declared metadata. Drop `block` (and the trailing `content` param, which only `block` mode uses):

  ```brink
  @[convention(claims = "^(?<name>[A-Z]+)$", order = 10, attach = Cue)]
  fn cue(name: string): Cue {
    return Cue { speaker: name };
  }
  ```

If the two handlers genuinely need to cooperate (one wraps, a *different* handler attaches), declare them as separate `@[convention]` handlers with distinct patterns and `order` values rather than combining both clauses on one.
