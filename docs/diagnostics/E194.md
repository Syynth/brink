# E194: a knot's temp is not visible from its stitches

A `~ temp` (`~ let` on the native surface) declared at a knot's own root is
read from one of that knot's stitches. Brink plays this correctly — a knot
and its stitches share one call frame and one `TempMap`, so the read
resolves to the declaration's own slot — but inklecate rejects the
identical program at compile time (`Unresolved variable: n`). Brink accepts
a strict superset of ink here, which is exactly what the **compat-deny**
tier exists to name.

**`Error`-tier by default and `[lints]`-overridable, all the way to
`allow`.** Unlike almost every other `Error`-default diagnostic, a project
may turn this one down deliberately — see "Fixing it" below.

## Explanation

`brink_ir::lir::lower::temps::alloc_temps` walks a knot's own body plus
every one of its stitch bodies before lowering begins and gives each `~
temp` name one slot in that shared frame — so, mechanically, nothing stops
a stitch from reading a name only the knot's root declares. The program
compiles and plays.

Ink's own compiler does not extend a knot's `~ temp` visibility into its
stitches at all. A stitch is, for `~ temp` purposes, a separate scope from
its knot's root content — referencing the knot's temp from inside a stitch
is `Unresolved variable` in inklecate, full stop, independent of whether
the divert that entered the stitch happened to run the declaration first:

```ink,fires(E194)
-> k
=== k ===
~ temp n = 7
-> s
= s
Stitch sees {n}.
-> END
```

By default this does not compile at all (`E194` is `Error`-tier); once
downgraded (see "Fixing it" below) it plays `Stitch sees 7.` in brink,
while inklecate rejects it outright — the declaration having already run
when the divert reaches `s` makes no difference to ink's compiler. That is
what separates this from
[`E193`](E193.md): `E193` is a genuine dominance question (did the
declaring statement run *on this path* before the read?) that the runtime
resolves the same way ink's runtime does, by substituting a default and
warning. This is not a runtime question at all — ink's compiler refuses the
reference regardless of the runtime path, so there is no runtime fallback
to lean on the way `E193`'s has.

**Why compat-deny, not a plain warning.** `docs/compiler-spec.md`
"Compat-deny diagnostics" (issue #3373, RULED 2026-09-01) names the tier:
"inklecate rejects this; brink can run it; you must opt in." Defaulting to
`Error` matches inklecate's own hard rejection, so an ink-compat project
sees the same wall Inky would show it. What makes the tier different from
an ordinary hard error is the admission invariant: brink genuinely produces
a *working* program once a project opts in, so the code stays
`[lints]`-overridable rather than staying a permanent, non-negotiable
error — the ruling's own words: "we should allow it to be turned off if the
user wants, it's annoying."

**What does not fire.** A stitch parameter of the same name is bound at
call time and is never reported. A stitch that declares its *own* `~ temp`
of the same name shadows the knot's for that stitch's reads entirely — that
is [`E193`](E193.md)'s question (does the stitch's own declaration dominate
its own reads?), not this one. A read inside the knot's own root body, or
inside another stitch that itself declares the name, is untouched by this
check.

## Example

```ink,fires(E194)
-> k
=== k ===
~ temp n = 7
-> s
= s
Stitch sees {n}.
-> END
```

compiles, by default, with:

```
[E194] a knot's temp is not visible from its stitches: `n` is read here, but the `~ temp n` that declares it belongs to knot `k`'s own root — ink does not consider a knot's `~ temp` visible from its stitches, so this compiles and plays here but inklecate rejects it (`Unresolved variable: n`)
```

and, because the default severity is `Error`, does not produce a program at
all — the compile call returns the diagnostic rather than a story. Once a
project downgrades the code (see "Fixing it"), the same source compiles and
plays `Stitch sees 7.` with no runtime warning: the declaration already ran
before the divert reached the stitch, so `Opcode::GetTemp` reads a written
slot.

The native surface spells the declaration `~ let` and reports the same
message with native vocabulary (`` `~ let n` ``, `` flow `k` ``) — pinned
by the compiler's own regression tests rather than reproduced as a doc
fence here, since a nested native stitch-shaped `flow` reached by a divert
from its enclosing `flow`'s root needs more structure than one in-memory
fence source string represents.

## Fixing it

Three honest options, in the order the ruling itself suggests trying them:

**Restructure so the stitch doesn't need the knot's temp.** If the value
only matters within the stitch, declare it there instead:

```ink,contrast
-> k
=== k ===
-> s
= s
~ temp n = 7
Stitch sees {n}.
-> END
```

**Promote it to a `VAR`.** If the value genuinely needs to survive from the
knot's root into its stitches, it was never frame-local to begin with — a
`VAR` is visible everywhere and always initialized:

```ink,contrast
VAR n = 0
-> k
=== k ===
~ n = 7
-> s
= s
Stitch sees {n}.
-> END
```

**Turn the code down.** If a project leans on this superset behavior
deliberately — the pattern is common enough in hand-written ink-adjacent
content that the ruling calls it "annoying" to have blocked outright —
`[lints]` reaches all the way to `allow`, not just `warn`:

```toml
[lints]
E194 = "allow"
```

or, kept as a warning that still compiles and plays while flagging the
non-portability to a real ink toolchain:

```toml
[lints]
E194 = "warn"
```

The CLI's `--allow`/`--warn`/`-D`/`--deny` flags reach the same code the
same way (`brink compile --allow E194`), and a `brink.toml`'s `[lints]`
entry travels with the project — a host consumer running `brink compile`
(a game build, `bevy-brink`'s asset pipeline) gets exactly the permissiveness
the studio does; there is no studio-only switch.
