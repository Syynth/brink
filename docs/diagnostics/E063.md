# E063

## Summary

A param/return type annotation disagrees with the type TM-1's body inference would otherwise derive (`annotations::mismatches`, TM-2's signature firewall), or a call through a `temp`/param value whose known type is a concrete non-function type, the wrong arity, or a mismatched argument (`strict::check_value_calls`, T1c calls-through-value) — plus the sibling declaration-initializer, plain-assignment, and UFCS-desugared-call producers listed in `docs/compiler-spec.md`'s E063 row. Both of the two producers this page documents run **only** when the effective type policy is `Strict`: that is the hedge this page used to carry ("advisory only... gradual policy"), and TM-3 has since settled it the other way — under `types = gradual`, under either dialect, neither producer runs at all, and whenever either does fire its severity is `Error`, never merely advisory.

## Explanation

Two independent producers reach this page, gated by the same `TypePolicy::Strict` check and reported through the same code, but otherwise unrelated:

**1. Annotation vs. body-inference mismatch** (`brink_analyzer::annotations::mismatches`, TM-2's "annotation = firewall"). For each named knot and stitch, this compares its own declared param/return type annotations against the body-inferred types `infer_project` derives independently, and reports a disagreement — `Unknown`/`Conflicted` body types never disagree (an unconstrained or genuinely-conflicting body offers nothing an annotation could contradict), and `unify(annotation, body) == annotation` covers the one legal directional coercion (`int` body, `float` annotation).

**2. Calls through a value** (`brink_analyzer::strict::check_value_calls`, docs/t1c-spec.md §4/§8). For the same named-knot/stitch set, this walks every recorded [`ValueCallFact`] — a call site whose callee is a `temp`/param rather than a knot, external, or annotated function value — and reports the ones whose *known* (non-`Unknown`, non-`Conflicted`) type disagrees with being called: a concrete non-function type (`NotCallable`), the wrong argument count (`ArityMismatch`/`OverBind`), or a mismatched argument type (`ArgMismatch`). A callee whose type escapes inference as `Unknown` or `Conflicted` is reported too, but as **`E065`**/**`E066`** respectively, not E063 — see "What does NOT fire".

Both producers are wired inside `strict::check`, which `strict_diagnostics` (`crates/internal/brink-analyzer/src/lib.rs`) invokes only `if opts.type_policy() == TypePolicy::Strict`; under `Gradual` the whole block — inference included — is skipped, so neither producer runs at all, confirmed empirically:

| Effective policy | Annotation mismatch (`hp: string` vs. int-inferred body) |
|---|---|
| `Brink`, `types` unset (→ `Strict`, `resolve_type_policy`) | `E063`, `Severity::Error` |
| `Brink`, `types = gradual` | compiles clean — no diagnostic |
| `Brink`, `types = strict` | `E063`, `Severity::Error` |

`resolve_type_policy` (`strict.rs`) is why an unset `types` under `Dialect::Brink` defaults to `Strict` while the same unset `types` under `Dialect::StrictInk` defaults to `Gradual` — "brink dialect" and "strict typing" read as independent axes but a bare `dialect = brink` project is running `Strict` by default unless `types = gradual` is set explicitly. `StrictInk` can never reach `Strict` at all: `types = strict` under `dialect = strict-ink` is a project-level config error, `E064`, reported instead of running `strict::check` (TM-2's annotation syntax is brink-extension syntax, so strict typing requires the brink dialect).

`effective_severity` (`strict.rs`) additionally hard-codes E063 to `Severity::Error` whenever `types == Strict` — but since both producers on this page already require `types == Strict` to run at all, in practice every E063 diagnostic either of them reports is `Error`; `DiagnosticCode::E063`'s own declared base severity (`Warning`) never actually surfaces for these two producers as currently wired.

## When this fires

- **Annotation mismatch**: a named knot's or stitch's own `param: Type` or `(): Type` return annotation disagrees with what body inference derives for that param/return slot — only under the effective `Strict` policy (`Brink` with `types` unset or `types = strict`; never `types = gradual`, under either dialect).
- **Value-call mismatch**: a call site inside a named knot or stitch (`{count(1, 2)}` where `count` is a `temp`/param, not a knot/external/annotated-function-value) whose callee's known type is a concrete non-function type, or whose call supplies the wrong number/type of arguments against a *known* function type — same `Strict`-only gate as above.

## What does NOT fire

- **Under `types = gradual`, under either dialect** — neither producer on this page runs at all; `strict::check` (and the `infer_project` inference pass it needs) is never invoked, so a value-call mistake like `~ temp count = 10` + `{count(1, 2)}` compiles clean and faults at runtime instead, with `RuntimeError::NotCallable` (issue #2872, `crates/brink-compiler/tests/issue_2872_e063_policy_audit.rs`).
- **A value-call mistake in the file's root/entry flow** (before the first `===` heading, or otherwise outside any named knot/stitch) — `check_value_calls` walks only `hir.knots` and their stitches; `HirFile.root_content` is a separate field the walk never visits. The same mistake that fires E063 inside a named knot compiles clean under **every** dialect × policy combination, `Brink` + `Strict` included, when moved to the root flow, and faults at runtime instead. This contradicts `docs/t1c-spec.md` §4's own "a strict-mode author can never reach the runtime fault" guarantee; that gap is tracked, unresolved, as **issue #2880** — this page documents the code's current (narrower) behavior, not the spec's ruled-but-not-yet-true guarantee. (A param-shaped version of the same mistake cannot live in the root flow at all — a param only exists inside a knot's own parameter list — so this gap is `~ temp`-only.)
- **A callee whose type escapes strict inference as `Unknown`** — reported as `E065`, not E063 (annotate the callee, or restructure so its type is inferable).
- **A callee whose type is `Ty::Conflicted`** — reported as `E066`, not E063 (the body's own uses of the callee genuinely disagree with each other; no annotation resolves that).
- **A knot, `EXTERNAL`, or a `VAR`/param annotated `fn(T…): R`** used as the callee — these are legitimately callable and never reach `check_value_calls`'s mismatch arms at all.

## Example

**Annotation mismatch** (`annotations::mismatches`) — `hp` is annotated `string`, but its only use compares it against an int literal, so body inference derives `int`:

```ink
-> heal(5)
=== heal(hp: string) ===
{hp > 1:
  ok
}
-> DONE
```

Under `--dialect brink` with `types` left unset (or `types = strict` explicitly), this reports `E063: annotated type \`string\` disagrees with the type inferred from usage (\`int\`)` at the annotation. Under `types = gradual`, it compiles clean.

**Value-call mismatch** (`strict::check_value_calls`) — `count` is a `temp` int, then called as if it were a function, inside a named knot:

```ink
-> main
=== main ===
~ temp count = 10
value: {count(1, 2)}
-> DONE
```

Under the same effective-`Strict` combinations, this reports `E063: \`count\` has type \`int\` — not callable (a \`fn(T…): R\` function value is required in call position)`. Moving the identical two lines above the first `=== main ===` heading (the file's root/entry flow) makes it compile clean under every dialect/policy combination, `Strict` included — see "What does NOT fire" and issue #2880.

Both shapes, across every `(Dialect, TypePolicy)` combination, are pinned end-to-end (compile, and — for every clean-compile cell — link and run through `brink_runtime::Story` to confirm the real `RuntimeError::NotCallable` fault) in `crates/brink-compiler/tests/issue_2872_e063_policy_audit.rs`.

## Fix

- **Annotation mismatch**: either the annotation or the body usage is wrong — fix whichever one doesn't match the author's actual intent. There is no reasonable way to "fix" by suppressing this one, since the annotation is the boundary contract TM-2 exists to enforce.
- **Value-call mismatch**: rename the local so it isn't confused for a function, or, if a function value genuinely belongs there, annotate the local's declared type as `fn(T…): R` so `check_value_calls` can see it's meant to be called and stops treating it as a plain value.
- **If the mistake sits in the file's root/entry flow under `types = strict`**: moving the offending lines inside a named knot (e.g. wrapping them in a small `=== helper ===` and diverting to it) makes the same check apply and turns the mistake into a compile-time E063 instead of a runtime `NotCallable` fault, until issue #2880 is ruled and (if the maintainer rules that way) `check_value_calls` is widened to scan `root_content` directly.
- **If the mistake is only ever going to be reached under `types = gradual`**: today, neither producer on this page runs at all under `Gradual` — there is no way to opt just this one check back on. The runtime fault (`RuntimeError::NotCallable`) is the only signal you get; catching it statically means switching the project's effective policy to `Strict`.
