# E095

## Summary

`#@was(name)` names the thing's own *current* name — a self-alias that would be a no-op entry in the compiled alias table. Nothing to migrate; likely a stale directive left over from a previous rename (warning, modules-spec §5/§7).

## Fix

**Safe** (`docs/autofix-spec.md` §3), **with one narrowing guard**: delete
the stale `#@was(...)` tag line.
`crates/internal/brink-ide/src/stale_was_fix.rs`'s `StaleWasFixer` offers
this fix whenever `E095` fires — on a knot, a top-level or nested stitch, a
`VAR`/`CONST`/`LIST`/`EXTERNAL` declaration, and the file-level module
rename record alike — **except** when the same physical `#@was` line is
also read by a *different* owner than the one that diagnosed it, and that
other owner's reading is a live, non-self rename rather than a coincidental
self-alias. This happens because a `#@module`'s file-level `#@was` and a
following top-level declaration's own lookback can both claim one physical
line (an entirely ordinary authoring style — `#@was` sitting directly above
the file's first `VAR`/`CONST`/`LIST`/`EXTERNAL`, no blank line between
them): `#@module(town)` / `#@was(town)` / `VAR gold = 0` self-aliases the
module, but the same line is also `VAR gold`'s own live `town -> gold`
rename; the mirror shape, `#@was(gold)` self-aliasing the `VAR` while
`#@module(town)` differs, has the module's alias as the one that would be
lost. The fixer withholds the fix outright in both shapes rather than
guessing which side "really" owns the line — see that module's own doc for
the narrowing check.

Outside that overlap it is mechanically `Safe`: every lowering site that
reads `#@was` compares the old name against the target's *current* name
before storing anything, so a self-aliasing occurrence never reaches
*that owner's* alias-table codegen — `ModuleDecl.was`/the declaration's own
`was` field is left `None` for that occurrence regardless of whether the
fix runs. Deleting the tag can't change the compiled artifact (bytecode,
alias table, exported line table) that owner contributes to. (A
self-aliasing `#@was` is *not* invisible to every pass, though: the flat
syntactic sweep behind `hir.was_directives` still sees it, and
`brink_analyzer::dialect_gate` flags one `E051` per occurrence under
`StrictInk` and `brink_ir::hir::emit_native` refuses to re-emit a file that
carries any — deleting the tag only ever removes those, never adds one.)
Proven by `brink_test_harness::fix::assert_safe_fix` over `tests/fix/E095/`
(`crates/internal/brink-test-harness/tests/fix_safe_obligations.rs`).

A `#@was` naming a genuinely different old name from the owner that
diagnosed it is untouched — the fixer only reacts to `E095` itself, never
widening beyond the self-alias shape. The fixer also has no reach into
NS-A2's `@[was(name)]` annotation-line spelling, which can self-alias and
raise `E095` too — an `ANNOTATION_LINE` isn't a `TAG_LINE`, so no fix is
offered there (a real gap, not a claim that the shape is unreachable).
